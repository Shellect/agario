# Теория блока

Текст для лекций. Примеры привязаны к каркасу agar.io: `TcpSession`, `UdpServer`, пустой клиент, общий `protocol`. Код занятий лежит в `materials/code/`. Этот файл не заменяет план пар (`01-plan-konspekt.md`) и задания (`03-zadaniya.md`).

Студенты уже умеют писать классы, функции, контейнеры, потоки, лямбды и сокеты через Asio. Не хватает модели: что такое объект как значение, что такое объект как ресурс, кто его хранит, когда он уничтожается и какой код имеет право его менять.

## 1. Две семантики: значение и ресурс

В C++ один и тот же синтаксис класса прячет две разные вещи.

**Значение** определяется содержимым. Два `Vector2{1, 2}` взаимозаменяемы. Копия — нормальная операция: получились два независимых набора чисел. Уничтожение одного не затрагивает другой. Таким должен быть вектор позиции, направление ввода, пакет как набор байтов после того, как он уже скопирован в буфер.

**Ресурс** определяется идентичностью. Сокет — это не «число дескриптора», а право пользоваться конкретным соединением операционной системы. Мьютекс — право входить в конкретную критическую секцию. `TcpSession` владеет сокетом. Копия сессии по умолчанию копирует дескриптор как целое. Получаются два объекта, которые оба считают соединение своим. Оба деструктора вызовут закрытие. Второй `close` попадает либо в уже закрытый дескриптор, либо — хуже — в дескриптор, который ОС уже выдала новому клиенту.

Отсюда правило, которое стоит повторять на каждой паре:

- тип без внешнего ресурса копируют и сравнивают по содержимому;
- тип с ресурсом, у которого есть идентичность (сокет, файл, мьютекс, поток, буфер, отданный в асинхронную операцию), не копируют;
- сырой указатель и ссылка означают «я не владею»;
- `std::unique_ptr` означает «владею один»;
- `std::shared_ptr` означает «владеем вместе, последний уничтожает».

`UdpServer& udp_` внутри `TcpSession` — как раз невладеющая ссылка. Сессия обязана не пережить сервер, но она его не удаляет. Это другой контракт, чем у `tcp::socket sock_`, который лежит в сессии по значению и умрёт вместе с ней.

Путаница студентов обычно такая: «раз в языке есть конструктор копирования, его надо оставить». Конструктор копирования по умолчанию — не услуга, а молчаливое решение компилятора: почленно скопировать поля. Для `float` это верно. Для сокета это ошибка модели.

## 2. Время жизни: когда объект существует

Объект существует между завершением конструктора и началом деструктора.

Автоматический объект (локальная переменная) уничтожается при выходе из блока, в том числе по `return` и по исключению. Поле объекта уничтожается как часть объекта-хозяина, после тела деструктора хозяина, в порядке, обратном объявлению полей. Динамический объект живёт, пока его не уничтожит владелец: `delete`, деструктор `unique_ptr` или последний `shared_ptr`.

Пока конструктор не закончился, объект не находится под управлением `shared_ptr`, даже если выражение `make_shared` уже начало работу. Поэтому `shared_from_this()` в конструкторе — неопределённое поведение. Их `TcpSession::start()` вызывается снаружи, после `make_shared`. Это правильное место.

Связанное наблюдение: деструктор — часть интерфейса, даже если он пустой у наследника. Поля наследника уничтожаются только если деструктор наследника вообще вызвался. Если удалять объект через указатель на базу без виртуального деструктора, язык вызывает только деструктор базы. Поля наследника не освобождаются. Для `unique_ptr<Entity>` это означает: `virtual ~Entity() = default` обязателен, иначе контейнер мира тихо ломает наследников.

Исключение не отменяет деструкторы уже построенных объектов. Именно на этом держится RAII. Если деструктор сам бросает исключение во время раскрутки стека, программа вызывает `std::terminate`. Учебное правило: деструктор не бросает.

## 3. RAII

RAII (получение ресурса есть инициализация) — привязка ресурса к времени жизни объекта. Конструктор получает ресурс или принимает его во владение. Деструктор освобождает. Все промежуточные выходы из функции становятся безопасными, потому что компилятор сам вставляет вызовы деструкторов.

`std::lock_guard` — маленький класс ровно с этой идеей. Конструктор вызывает `mutex.lock()`, деструктор — `unlock()`. Ранний `return` и исключение из `boost::asio` не оставляют мьютекс занятым. В `UdpServer::registerClient` это уже сделано. Голые `lock()` / `unlock()` хуже не стилем, а тем, что каждая ветка обязана помнить про `unlock`. Одна забытая ветка — взаимная блокировка, которую компилятор не видит.

`std::unique_ptr` — RAII для одного владельца в куче. `std::vector` — RAII для непрерывного буфера: деструктор вектора уничтожает элементы и освобождает память. `World` из материалов поэтому не имеет ручной очистки. Когда `World` уничтожается, уничтожается вектор, уничтожаются `unique_ptr`, вызываются виртуальные деструкторы сущностей.

`tcp::socket` как поле — тоже RAII: деструктор сокета закрывает соединение. Отдельный метод `close()` нужен, чтобы закрыть раньше, не дожидаясь уничтожения сессии. Пустой `TcpSession::close()` в текущем коде как раз дыра: ошибка чтения вызывает `close()`, а сокет остаётся открытым, пока жив `shared_ptr`.

Граница RAII, которую студенты пропускают: деструктор освобождает ресурс объекта, но не отменяет уже запущенную асинхронную операцию саму по себе, если колбэк ещё держит `shared_ptr`. Пока колбэк не закончился, сессия жива, деструктор не начнётся. Это не утечка «навсегда», это продление жизни на время операции. Утечка получается, когда колбэк хранит `shared_ptr` на сессию, а сессия хранит этот колбэк и никогда его не отпускает. Тогда счётчик не падает до нуля. Лекарство на этом блоке только назвать: на одной из сторон держать `weak_ptr`.

## 4. Специальные функции и правило пяти

Компилятор умеет генерировать:

- конструктор по умолчанию;
- конструктор копирования;
- копирующее присваивание;
- конструктор перемещения;
- перемещающее присваивание;
- деструктор.

Если программист объявил хотя бы одну из операций копирования, перемещения или деструктор, легко получить набор, который больше не соответствует владению. Правило пяти: если класс управляет ресурсом и вы написали одну из этих шести функций, подумайте про остальные пять. Часто правильный ответ — не писать их телом, а запретить.

Для `TcpSession`:

```cpp
TcpSession(const TcpSession&) = delete;
TcpSession& operator=(const TcpSession&) = delete;
TcpSession(TcpSession&&) = delete;
TcpSession& operator=(TcpSession&&) = delete;
```

Почему удалён и move. Перемещение сокета технически возможно, но сессия в этом проекте живёт только внутри `shared_ptr`. Её не кладут в `vector<TcpSession>`. Полуперемещённый объект с пустым сокетом студенты всё равно уничтожают и снова закрывают «что-то». Проще запретить обе операции и оставить один канал владения — `shared_ptr`.

`= delete` в публичной секции лучше старого приёма «объявить копирование в `private` и не определять». При `= delete` ошибка возникает в точке вызова и прямо говорит, что операция запрещена.

Для `Vector2` правило пяти не нужно. Числа не ресурс. Почленная копия и есть правильное поведение. Писать пустой деструктор «для солидности» вредно: он подавляет некоторые оптимизации и намекает читателю, что в типе есть ручное управление.

`noexcept` на перемещении и на простых методах вроде `Vector2::length` — обещание не бросать. `vector` при переаллокации опирается на небросающее перемещение. Для сокета, если move когда-нибудь появится, он тоже должен быть `noexcept`: переместить дескриптор — значит скопировать целое и обнулить источник, исключению там неоткуда взяться.

## 5. const как контракт

`const` на методе означает: метод не меняет наблюдаемое состояние объекта. Его можно вызвать у `const TcpSession&` и у временного объекта, который функция обещала только читать.

Кандидаты в их коде: «сокет открыт?», «адрес клиента», «радиус», «позиция», «разобрать тело пакета». Разбор байтов в структуру не должен менять сессию. Поэтому `read_input` в учебных материалах — свободная функция, которая только читает `vector`.

`const` на параметре-ссылке (`const Entity&`) означает: функция не копирует объект и не меняет его. Для базы полиморфной иерархии это ещё и способ вызвать виртуальную функцию без среза: объект не копируется в параметр по значению.

Чего `const` не делает. Он не делает метод потокобезопасным сам по себе. Два потока могут читать один объект без синхронизации, только если никто одновременно не пишет. Он не даёт скорости «автоматом». `const std::string getName() const`, где `const` стоит на возвращаемом по значению типе, — устаревшая привычка: такой возврат мешает перемещению.

`mutable` разрешает менять поле внутри `const`-метода. Законный случай в этом проекте — мьютекс: логически «прочитать карту клиентов» не меняет карту, но мьютекс при захвате меняет своё внутреннее состояние. Поэтому поле мьютекса часто объявляют `mutable`, если появятся const-геттеры. Незаконный случай — пометить `mutable` радиус игрока, чтобы `const`-метод мог его увеличить. Тогда `const` врёт.

## 6. Композиция и наследование

Композиция: объект содержит другой объект (или владеющий указатель на него) и распоряжается его жизнью. `World` содержит вектор сущностей. `TcpSession` содержит сокет и буфер. Это основной способ связи в проекте.

Агрегация в учебном смысле этого блока: объект хранит ссылку или указатель и не уничтожает чужой ресурс. `TcpSession` хранит `UdpServer&`.

Наследование: производный класс является разновидностью базового и может подменить поведение виртуальных функций. `Player` и `Food` являются `Entity`, потому что миру нужно обходить их единообразно: `update`, `radius`, `position`. Наследование не нужно, чтобы «переиспользовать поля». Если общий код — это три числа, их проще положить в `Vector2` или в маленькую структуру и включить полем.

Признак, что наследование лишнее: у базы нет ни одной виртуальной функции, наследник не подменяет поведение, удаление через базу не планируется. Тогда это композиция, записанная неудобным синтаксисом.

`final` на `Player` и `Food` фиксирует решение: от них дальше не наследуют. Меньше соблазна построить глубокое дерево «еда → большая еда → особенная еда».

## 7. Виртуальные функции, срезка, полиморфизм

Обычная функция связывается на этапе компиляции по типу выражения. Виртуальная — на этапе выполнения по типу реального объекта. Вызов `entity->update(dt)`, где `entity` имеет тип `Entity*`, попадает в `Player::update` или `Food::update` в зависимости от того, какой объект создали.

Механизм — таблица виртуальных функций у объекта. Для курса достаточно следствий, не устройства компилятора:

- вызов через значение базы не видит наследника, потому что наследника в этом значении нет;
- вызов через указатель или ссылку на базу видит наследника;
- деструктор базы должен быть виртуальным, если `delete` или `unique_ptr<Base>` уничтожает наследника.

Срезка (slicing): `Entity e = player;`, если бы `Entity` был конкретным, скопировала бы только поля базы. Хвост `Player` выброшен. Виртуальные вызовы на `e` идут в базу. Поэтому мир хранит `unique_ptr<Entity>`, а не `vector<Entity>`. Абстрактный класс с чистой виртуальной функцией (`virtual void update(float) = 0`) дополнительно запрещает случайно создать «просто Entity» и случайно положить его в вектор по значению: такой вектор не компилируется.

`override` заставляет компилятор проверить, что метод действительно перекрывает виртуальный метод базы. Опечатка в сигнатуре без `override` создаёт новую функцию, и полиморфизм молча пропадает. `override` — не украшение.

Чего полиморфизм не заменяет. `dynamic_cast` в учебном `World::eat` — сознательный компромисс: на этой стадии студенты различают еду и игрока типом, а не отдельным перегруженным `on_eaten`. Это слабое место модели, его полезно назвать. Более ровный вариант позже: виртуальная функция «что делать при столкновении», без лестницы `dynamic_cast`. В блоке достаточно, чтобы студенты увидели цену такого кода: каждый новый вид сущности заставляет дописывать ветки в `World`.

Полиморфизм работает только там, где объект ещё цел. Указатель на базу не продлевает жизнь. Продлевает владелец: `unique_ptr` в мире или `shared_ptr` сессии.

## 8. Умные указатели: кто имеет право удалить

`unique_ptr<T>` нельзя скопировать. Его можно переместить. В каждый момент ровно один владелец. Для клеток мира это естественная модель: клетка принадлежит миру, клиент её не удаляет, сессия её не хранит у себя в поле навсегда.

`shared_ptr<T>` копируется. Копия увеличивает счётчик. Объект удаляется, когда счётчик стал нулём. Для сессии Asio это естественная модель: и контейнер сервера, и висящий колбэк чтения должны иметь право сказать «я ещё использую соединение».

`weak_ptr<T>` не владеет. `lock()` либо даёт временный `shared_ptr`, либо пустоту, если объект уже умер. Нужен, когда наблюдать надо, а продлевать жизнь нельзя.

Сырой `T*` в сигнатуре функции на этом курсе читается как «вызывающий гарантирует, что объект жив на время вызова, функция не удаляет». Поле класса типа `T*` без комментария, кто удаляет, — дефект ревью.

`make_unique` / `make_shared` предпочтительнее явного `new`, потому что размер выделения и владение собираются в одном выражении. `new` без `delete` в проекте запрещён правилом блока, не потому что `new` «плохой оператор», а потому что у студентов уже есть Asio и исключения: ручная пара легко рвётся.

Цикл `shared_ptr`: A хранит B, B хранит A, снаружи указателей не осталось, счётчики равны 1, оба живут до конца процесса. В сессии цикл выглядит так: поле хранит функцию, функция захватила `shared_ptr` на эту же сессию. На паре достаточно схемы на доске, без отдельной лабораторной.

## 9. Лямбды и асинхронность

Лямбда — объект с оператором вызова. Захват — это поля этого объекта, которые инициализируются в момент создания лямбды.

`[&]` сохраняет ссылки на автоматические переменные. Это верно, только если лямбду вызовут до выхода из этих переменных. `std::sort` так и делает. `async_read` так не делает: функция `doReadHeader` возвращается сразу, колбэк вызовется позже из `io_context::run`. Ссылки уже висят на мёртвый стек.

`[=]` и инициализирующий захват копируют значения сейчас. Копия `int` безопасна. Копия `TcpSession*` (захват `[this]`) безопасна только пока сессия жива. Отключение клиента как раз уничтожает сессию раньше колбэка.

`[self = shared_from_this()]` копирует `shared_ptr`. Счётчик увеличивается. Сессия не уничтожится, пока эта копия лежит внутри лямбды, то есть до конца колбэка. Их `doReadHeader` и `doReadBody` уже написаны так. Теория пары в том, чтобы студент не «упростил» это до `[this]`.

Смешанный захват `[&, self = shared_from_this()]` почти всегда ошибка: сессию продлили, а соседние локальные переменные всё равно захватили по ссылке.

Буфер, который Asio читает, должен жить до вызова колбэка, не только до возврата из `async_read`. Поле `hdr_` у сессии годится, потому что `self` держит сессию. Локальный массив в `doReadHeader` не годится. Локальный `uint8_t out[4]` внутри колбэка годится только для синхронного `write`, который заканчивается до выхода из колбэка. Этот `write` плох по другой причине: он блокирует поток `io_context`, и буфер в текущем коде не инициализирован. Асинхронная запись требует, чтобы байты ответа лежали в поле или в блоке памяти под `shared_ptr`, захваченном лямбдой записи.

`shared_from_this` требует, чтобы класс наследовал `std::enable_shared_from_this<СамКласс>` и чтобы текущий объект уже принадлежал `shared_ptr`. Оба условия в их `TcpSession` и `UdpServer` выполнены, если объекты создают через `make_shared`, а не на стеке.

Один колбэк приёма UDP, который снова вызывает `doReceive` только в конце, даёт цепочку: вторая операция не начинается, пока первая не завершилась. Поле `sender_` тогда не гоняется само с собой. Это тонкость: отсутствие мьютекса вокруг `sender_` сейчас спасает не «UDP вообще потокобезопасен», а то, что незавершённых приёмов один. `clients_` меняется и из этого колбэка, и из `registerClient`, который могут вызвать с TCP-потока. Карта уже под `lock_guard`. Эндпоинт в `registerClient` передаётся по значению — копия, а не ссылка на `sender_`. Это правильная граница.

## 10. Мьютекс, критическая секция, что им не является

Гонка данных: два потока обращаются к одному объекту памяти, хотя бы один пишет, синхронизации нет. Это неопределённое поведение, не «иногда старое значение».

Мьютекс делает критическую секцию. `lock_guard` ограничивает секцию блоком. Секция должна быть короткой. Внутри неё не запускают операцию, которая ждёт другой поток, и по возможности не запускают `async_*`, если обработчик завершения снова берёт тот же мьютекс: легко получить самоблокировку.

`std::scoped_lock` захватывает несколько мьютексов сразу и в фиксированном порядке, чтобы два потока не взяли их навстречу. Пока в коде один мьютекс на карту клиентов, хватает `lock_guard`.

Мьютекс не сериализует логику Asio целиком. Есть другой инструмент той же библиотеки — `strand`: очередь обработчиков, которые не исполняются параллельно. В этом блоке его достаточно назвать. Студенты уже видели мьютекс; `strand` — следующий слой, когда один `io_context` крутят несколько потоков и хочется не расставлять `lock_guard` на каждое поле сессии.

`recursive_mutex` позволяет одному потоку захватить мьютекс повторно. В учебном сервере это симптом, что функция под замком снова зовёт функцию под тем же замком. Лечится разделением «работы под замком» и «работы снаружи», а не сменой типа мьютекса.

## 11. Исключения в объёме этого блока

Asio сообщает об ошибке операции двумя способами: код `error_code` в колбэке и исключения на некоторых синхронных API. Их чтение заголовка идёт через `error_code`. Это нормальный стиль: колбэк не должен выбрасывать наружу в `io_context` без общей политики.

Сильная гарантия (состояние объекта как до вызова, если вышло исключение) и базовая (объект разрушаем, без утечек) на курсе нужны как слова. Практический вывод один: ресурсы уже обёрнуты в RAII, поэтому исключение между `lock` и `unlock` не должно существовать как ручная пара. `lock_guard` даёт базовую безопасность для мьютекса автоматически.

`noexcept` нарушать нельзя: исключение из такой функции завершает программу. Деструктор ведёт себя так же, если исключение покидает его во время другой раскрутки.

## 12. Протокол как контракт, не как «ещё один класс»

Сообщение TCP в их каркасе: 1 байт типа, 2 байта длины по младшему байту вперёд, затем тело. Длина относится к телу, заголовок всегда 3 байта. Пока длина не прочитана и не проверена, к телу обращаться нельзя. `body_.resize(len)` без верхней границы позволяет клиенту попросить гигабайт. Это уже вопрос протокола: максимальный размер — часть контракта, не оптимизация.

Номера типов — один источник. `enum` в `protocol.h` начинается с нуля. В `tcp_session.cpp` сравниваются литералы `1` и `2`. Эти два места разъедутся при первом же новом сообщении. Теория здесь про целостность интерфейса: сервер и клиент зависят от `common`, а не копируют константы в каждый файл. Сборка одной библиотеки `agar_common` как раз про это.

`memcpy` в `float` определён только если размер совпал и объект байтов реально содержит представление `float`. Проверка `size >= 8` обязательна до копирования. Выравнивание для `memcpy` в промежуточный `float` нормально. Чтение `float` напрямую через приведение указателя на буфер сокета — отдельный риск выравнивания; учебный код копирует в локальную переменную.

Порядок байтов `float` в этом скелете — порядок машины. Для одного стенда с одинаковыми клиентом и сервером занятие можно провести. Ограничение надо сказать прямо: это не сетевой формат «для любой архитектуры». Вынести в известные пробелы: явный порядок байтов и целочисленная фиксированная точка.

## 13. Как темы закрывают белые пятна

| Пробел | Где проявляется в их коде | Теория, которой хватает в блоке |
| --- | --- | --- |
| Владение | сокет, буфер, карта клиентов, будущий мир | значение / ресурс, указатель не владеет |
| RAII | `lock_guard`, пустой `close`, сокет-поле | деструктор освобождает, исключения не обходят его |
| Копия и move | молчаливая копия `TcpSession` | правило пяти, `= delete` |
| const | геттеры, разбор пакета | контракт «не меняю», `mutable` только для мьютекса и кэша |
| Виртуальность | будущие `Player`/`Food` | деструктор базы, `override`, запрет среза |
| Композиция | мир, сессия, ссылка на UDP-сервер | владение полем против ссылки |
| Лямбды | `self` в `async_read`, соблазн `[&]` | захват живёт отдельно от кадра стека |
| Исключения | Asio, критическая секция | деструктор не бросает, замок через RAII |
| Протокол | enum против `type == 1` | один контракт в `common` |

За блоком остаются: множественное наследование, виртуальное наследование, выражение SFINAE и концепты глубже использования `unique_ptr`, свой оператор присваивания с сильной гарантией, аллокаторы, `enable_shared_from_this` в иерархии с двумя базами, `strand`, порядок байтов, авторитативная физика игры, сериализация снимка мира для UDP. Это список «мы знаем, что этого не проходили», его зачитывают на первой и последней паре.

## 14. Словарь, который студенты должны произносить

**Владелец** — тот, кто уничтожает объект.

**Наблюдатель** — ссылка, сырой указатель или `weak_ptr`.

**Значение** — копируется почленно и сравнивается по содержимому.

**Ресурс** — внешняя сущность с идентичностью; копия объекта её не удваивает честно.

**RAII** — ресурс приобретён в конструкторе и отпущен в деструкторе.

**Срезка** — копия в значение базового типа потеряла часть наследника.

**Полиморфный вызов** — вызов виртуальной функции через указатель или ссылку на базу.

**Продление жизни** — копия `shared_ptr` в захвате лямбды не даёт уничтожить сессию до конца колбэка.

**Гонка** — несинхронизированный доступ к одной памяти из двух потоков, один из доступов — запись.

**Контракт протокола** — размеры, коды и порядок полей, одинаковые у клиента и сервера, описанные в одном месте.
